## Probing ownership — don't break this

- The deployed Worker is **serve-only**: it never probes and never writes D1. `SERVE_ONLY` auto-enables on non-Node runtimes (workerd) or via env (`health-probe.ts:65`). `/api/probe` returns 403 on the Worker.
- All probing runs from `probe/nepal-probe.mjs` on a **Nepal-IP machine** (cron, every 5 min), writing hourly aggregates + current state straight to D1 via REST. The Worker renders that snapshot.
- Reason: probing from a foreign/datacenter IP marks healthy .np portals down (WAF blocks + strict-TLS rejection). Do not move probing into the Worker or a foreign vantage.
- `probe/nepal-probe.mjs` reads the same `CLOUDFLARE_*` vars and loads `.env.local` if present; `--dry-run` probes without writing. Do not edit `src/.../health-probe.ts` to "fix" probing behavior that's intentionally Node-vantage.
- The probe presents a **browser-like User-Agent** on purpose: .np WAFs reset/stall self-describing bot UAs (`kathmandu.gov.np`, `nea.org.np`), so a bot UA produces false "down". Keep it browser-like; don't "make it honest".
- **Verify the Worker's D1 secrets after any DB recreation.** The Worker's `CLOUDFLARE_D1_DATABASE_ID` must equal the DB the Nepal probe writes (`d1.ts` compares nothing); a stale id makes the serve-only worker's snapshot read fail and it silently falls back to self-probing from the Cloudflare datacenter → mass false "down". Symptom: served history is full of `o`/`d`/`x` but `wrangler d1 execute` on the configured DB shows sparse/`n` buckets.

## D1, history, and write limits

- D1 persistence is gated to every **5 minutes** (`PERSIST_INTERVAL_MINUTES`, min 1) even though probes run per cycle, to stay inside the free-tier 100k writes/day. Preserve this gating if you touch `persistChecks`/`runChecks`; history reads reuse a cached index between persist cycles.
- History is **hourly buckets** with worst-status-in-hour aggregation: a bucket counts as `down` if any sample that hour was down (`d1/schema.sql`, `persistChecks`). A 1-minute blip must not be hidden.
- Writes are batched in chunks of 60 via `d1BatchChunked` (`health-probe.ts:325`) — the D1 REST statement cap. Keep chunking for any large batch.
- D1 is reached through `src/lib/d1.ts` (plain REST, no native binding). Missing/invalid env → `d1Config` is null → the app serves `source: "simulated"` history; an *empty configured* DB yields grey "no data" slots, never fabricated bars.
- Env: `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_D1_DATABASE_ID`, `CLOUDFLARE_API_TOKEN` (token needs "D1: Edit"); copy `.env.example` → `.env.local`.

## Runtime split (Node vs Workers)

`IS_NODE` guards two Node-only behaviors that skip themselves on Workers (`health-probe.ts:55`): the relaxed-TLS retry (undici `Agent({ rejectUnauthorized: false })`) and TLS cert-expiry probing (`node:tls`, re-checked every 6h). Primary probes use platform `fetch`; the undici dispatcher is only for the TLS-relaxed retry.

## Workers / OpenNext deploy quirks

- `custom-worker.ts` imports `./.open-next/worker.js`, which is **generated by `opennextjs-cloudflare build`** and absent on fresh checkout — hence the `@ts-ignore`. Run the build (or `npm run deploy`) before touching it.
- `worker-polyfills.ts` must stay imported before the OpenNext worker: workerd lacks `MessagePort`/`MessageChannel` and Next's compiled edge primitives throw at module init without them.
- `wrangler.jsonc`: `name` must equal `WORKER_SELF_REFERENCE.service`, or deploy fails with error 10143 (OpenNext uses that binding for ISR revalidation).
- `npm run preview` / `deploy` / `upload` all run `opennextjs-cloudflare build` first. ISR (`revalidate = 60` on `/api/health`) needs the OpenNext cache binding to persist across cold starts.
